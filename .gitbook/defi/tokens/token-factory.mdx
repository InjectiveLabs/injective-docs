TokenFactory lets any account mint a native token without writing or deploying a contract. Denoms take
the form `factory/{creatorAddress}/{subdenom}`. Because they are namespaced by creator address,
creation is permissionless and there are no name collisions to resolve.

TokenFactory tokens are bank denoms, which is what makes them the preferred token launch method on Injective. The exchange,
auction, insurance and permissions modules all interface natively with bank denoms, so a TokenFactory token can be
traded on the native orderbook, used as collateral, or gated by compliance rules with no adapter in
between.

## What Admin Control Gives You

The sender of `MsgCreateDenom` is assigned as the denom's admin. The message carries no admin field,
so the initial admin is always the creator. TokenFactory allows admin reassignment through
`MsgChangeAdmin`, and the authority itself is stored in the native module as part of the denom's
authority metadata, not in contract code.

Admin authority exists to keep routine token operations out of governance. The admin mints, burns
where permitted, and updates name, symbol and decimals with a single message, effective immediately.
By contrast, peggy and IBC denoms have no admin. Their metadata is set automatically when the bridge
or transfer first creates them, and correcting it requires a governance proposal.

EVM originated denoms (`erc20:0x...`) follow a third model: authority lives in the token contract itself.
The bank precompile accepts `setMetadata`, mint and burn calls only from the paired contract, resolving
the denom from the calling address, so admin control is whatever the contract code grants, such as the
owner role of a `MintBurnBankERC20`. No TokenFactory admin record exists for these denoms and no
governance is required.

| Capability | Message | Notes |
|---|---|---|
| Mint to any account | `MsgMint` | Admin only, unless a permissions namespace overrides it |
| Burn from an account | `MsgBurn` | Requires `allow_admin_burn`, set at creation only |
| Set name, symbol, decimals | `MsgSetDenomMetadata` | Effective immediately, no governance needed |
| Transfer or renounce admin | `MsgChangeAdmin` | Renouncing makes supply immutable |
| Delegate to another account | `authz` grants | Share admin rights without transferring them |

Unlike contract based tokens, total supply is tracked and queryable through the bank module directly,
with no contract call required.

## What You Can Layer On Top

| Feature | What it gives you | Guide |
|---|---|---|
| **ERC20 pair** | MetaMask visibility and Solidity access, sharing one balance across native and Injective EVM | [ERC20 Module](/developers-evm/erc20-module) |
| **Permissions namespace** | Role based MINT, BURN, SEND, RECEIVE and SUPER_BURN control, plus KYC hooks | [Permissioned Assets](/developers-defi/permissioned-assets) |
| **Spot market** | A native orderbook market for the token | [Launch a Market](/developers-defi/market-launch) |
| **Registry listing** | Logos and labels in Injective dApp frontends | [Injective List](/developers/assets/injective-list) |

A TokenFactory denom is **not** visible to the EVM until you register an ERC20 pair. Until then,
MetaMask and Solidity contracts cannot see it. See
[MultiVM Token Standard](/developers-evm/multivm-token-standard).

## Choosing TokenFactory

| Instead of | Choose TokenFactory when |
|---|---|
| **Deploying on the Injective EVM** | Native admin control is necessary over supply and metadata rather than EVM based authority. An EVM deployment is the better fit if the token's logic lives in a contract |
| **CW20** | Always, for new work. See the deprecation notice below |

Tokens bridged into Injective via Wormhole are also TokenFactory denoms.

## Irreversible Choices

Three settings cannot be changed after the fact: `decimals` once nonzero, `allow_admin_burn` once
false or disabled, and metadata authority once the admin is renounced. The
[Launch a Token](/developers-defi/token-launch#2-decisions-you-cannot-reverse) guide covers each.

## CW20 Adapter

<Warning>
**CW20 is not recommended for new integrations and is planned for deprecation.** Use TokenFactory for
new tokens, and the [MultiVM Token Standard](/developers-evm/multivm-token-standard) where an ERC20
interface is needed. The CW20 adapter remains available for existing assets.
</Warning>

The `CW20AdapterContract` represents an existing CW20 asset as a TokenFactory denom of the form
`factory/{CW20_ADAPTER_CONTRACT}/{CW20_CONTRACT_ADDRESS}`. The adapter holds the CW20 tokens and mints
the factory denom; redeeming burns the denom and releases the CW20 back to the owner.

For conversion and redemption examples, see [CW20 Adapter](/developers-cosmwasm/cw20-adapter).
