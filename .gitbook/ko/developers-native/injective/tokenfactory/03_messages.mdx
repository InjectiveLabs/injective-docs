# 메시지

이 섹션에서는 tokenfactory 메시지의 처리와 해당 상태 업데이트에 대해 설명합니다.

## 메시지

### CreateDenom

denom 생성자 주소, subdenom 및 관련 메타데이터(name, symbol, decimals)가 주어지면 `factory/{creator address}/{subdenom}` 형식의 denom을 생성합니다. Subdenom은 `[a-zA-Z0-9./]`를 포함할 수 있습니다.
`allow_admin_burn`을 true로 설정하면 admin이 다른 주소에서 토큰을 소각할 수 있습니다.
```protobuf
message MsgCreateDenom {
  string sender = 1 [ (gogoproto.moretags) = "yaml:\"sender\"" ];
  // subdenom은 최대 44개의 "영숫자" 문자 길이가 될 수 있습니다.
  string subdenom = 2 [ (gogoproto.moretags) = "yaml:\"subdenom\"" ];
  string name = 3 [ (gogoproto.moretags) = "yaml:\"name\"" ];
  string symbol = 4 [ (gogoproto.moretags) = "yaml:\"symbol\"" ];
  uint32 decimals = 5 [ (gogoproto.moretags) = "yaml:\"decimals\"" ];
  // admin이 다른 주소에서 토큰을 소각할 수 있으면 true
  bool allow_admin_burn = 6 [ (gogoproto.moretags) = "yaml:\"allow_admin_burn\"" ];}
```

**상태 변경:**

- `Params`에 설정된 denom 생성 수수료를 생성자 주소에서 커뮤니티 풀로 전송합니다.
- bank keeper를 통해 `DenomMetaData`를 설정합니다.
- 생성된 denom `factory/{creator address}/{subdenom}`의 admin을 저장하기 위해 해당 denom에 대한 `AuthorityMetadata`를 설정합니다. Admin은 자동으로 Msg 발신자로 설정됩니다.
- 생성자별로 생성된 denom의 상태를 유지하는 `CreatorPrefixStore`에 denom을 추가합니다.

### Mint

발행 권한은 denom에
[permissions 네임스페이스](/ko/developers-native/injective/permissions)가 있는지 여부에 따라 달라집니다.

- **네임스페이스 없음:** 현재 admin만 발행할 수 있습니다. admin은 기본적으로 denom의 생성자로 설정됩니다.
- **네임스페이스 있음:** admin 검사를 완전히 건너뛰며, 발신자는 `MINT` 권한을 보유해야 합니다. denom admin인 것만으로는 충분하지 않습니다.

```protobuf
message MsgMint {
  string sender = 1 [ (gogoproto.moretags) = "yaml:\"sender\"" ];
  cosmos.base.v1beta1.Coin amount = 2 [
    (gogoproto.moretags) = "yaml:\"amount\"",
    (gogoproto.nullable) = false
  ];
  string receiver = 3 [ (gogoproto.moretags) = "yaml:\"receiver\"" ];
}
```

`receiver`가 비어 있으면 토큰은 발신자에게 발행됩니다.

**상태 변경:**

- 다음 안전 검사 수행
    - denom에 대한 bank 메타데이터가 존재하는지 확인, 그렇지 않으면 `ErrDenomDoesNotExist`
    - denom에 permissions 네임스페이스가 없으면 발신자가 denom의 admin인지 확인
    - denom에 permissions 네임스페이스가 있으면 발신자가 `MINT` 권한을 보유하고 있는지 확인
- `bank` 모듈을 통해 해당 denom에 대해 지정된 양의 토큰을 발행하고 receiver에게 전송

<Warning>
페어링된 ERC20을 통해 EVM에서 발행이 트리거되는 경우, 이 메시지의 발신자는 EVM 호출자가 아니라
**ERC20 컨트랙트 주소**입니다. 따라서 모듈의 admin 검사는 컨트랙트 주소를 대상으로 실행되며, 어떤 EVM 호출자가
발행을 트리거할 수 있는지는 컨트랙트 자체의 코드가 결정합니다. denom admin 키를 보유하고 있다고 해서 페어링된
컨트랙트를 통한 발행이 승인되는 것은 아닙니다. 컨트랙트 주소 자체가 admin이거나 `MINT` 권한을 보유해야 합니다.
필요한 구성은 [ERC20 모듈](/ko/developers-evm/erc20-module#민트-및-버닝-권한)을 참조하세요.
</Warning>

### Burn

소각 권한은 발행 권한보다 엄격하며, 두 가지 독립적인 요소에 따라 달라집니다:
발신자가 자신의 잔액에서 소각하는지 여부, 그리고 denom에 permissions 네임스페이스가 있는지 여부입니다.

```protobuf
message MsgBurn {
  string sender = 1 [ (gogoproto.moretags) = "yaml:\"sender\"" ];
  cosmos.base.v1beta1.Coin amount = 2 [
    (gogoproto.moretags) = "yaml:\"amount\"",
    (gogoproto.nullable) = false
  ];
  string burnFromAddress = 3 [ (gogoproto.moretags) = "yaml:\"burn_from_address\"" ];
}
```

`burnFromAddress`가 비어 있으면 기본값은 발신자이며, 이 경우 메시지는 자체 소각(self-burn)이 됩니다.

| 경우 | 네임스페이스 없음 | 네임스페이스 있음 |
|---|---|---|
| **자체 소각** (`burnFromAddress`가 발신자이거나 비어 있음) | 모든 보유자에게 허용 | 발신자가 `BURN`을 보유해야 함 |
| **다른 주소에서 소각** | denom에 `allow_admin_burn`이 설정되어 있고 **동시에** 발신자가 admin이어야 함 | denom에 `allow_admin_burn`이 설정되어 있고 **동시에** 발신자가 `SUPER_BURN`을 보유해야 함 |

**상태 변경:**

- 다음 안전 검사 수행
    - `burnFromAddress`를 확인하며, 기본값은 발신자
    - 위의 권한 매트릭스 적용
- `bank` 모듈을 통해 burn-from 주소에서 해당 denom에 대해 지정된 양의 토큰 소각

<Warning>
`allow_admin_burn`은 모든 burn-from에서 가장 먼저, 그리고 무조건적으로 검사됩니다. 이 값은
`CreateDenom` 시점에만 설정할 수 있으며 래치(latch)입니다. 한 번 false이거나 비활성화되면 다시는
활성화할 수 없습니다. 활성화를 시도하면 `cannot enable AdminBurnAllowed if it was previously disabled` 오류로 실패합니다.

이는 페어링된 ERC20 토큰에 중요합니다. ERC20 `burn()`은 컨트랙트를 발신자로, 보유자를 burn-from 주소로 하여
이 메시지에 도달하므로, 항상 burn-from이며 절대 자체 소각이 아닙니다. `--allow-admin-burn` 없이 생성된
denom은 페어링된 ERC20을 통해 절대 소각할 수 없습니다.
[ERC20 모듈](/ko/developers-evm/erc20-module#민트-및-버닝-권한)을 참조하세요.
</Warning>

### ChangeAdmin

denom의 admin을 변경합니다. 이는 denom의 현재 admin만 호출할 수 있습니다. admin 주소가 zero address로 설정된 후에도 토큰 보유자는 자신이 보유한 토큰에 대해 `MsgBurn`을 실행할 수 있습니다.

<Note>
denom admin을 변경해도 페어링된 ERC20 컨트랙트에는 영향이 없습니다. 페어가 `MintBurnBankERC20`을 배포한 경우,
해당 Solidity `owner()`는 이 메시지로 변경되지 않으며, ERC20 소유권을 이전해도 denom admin은 변경되지 않습니다.
두 권한은 서로 독립적입니다.
</Note>

```protobuf
message MsgChangeAdmin {
  string sender = 1 [ (gogoproto.moretags) = "yaml:\"sender\"" ];
  string denom = 2 [ (gogoproto.moretags) = "yaml:\"denom\"" ];
  string newAdmin = 3 [ (gogoproto.moretags) = "yaml:\"new_admin\"" ];
}
```

### SetDenomMetadata

특정 denom의 메타데이터 설정은 해당 denom의 admin에게만 허용되며, admin이 빈 주소로 설정된 후에는
governance에게 허용됩니다.
bank 모듈에서 denom 메타데이터를 덮어쓸 수 있습니다. admin은 활성화된 경우 admin burn 기능을 비활성화할 수도 있습니다.

<Warning>
**decimals는 한 번 설정되면 사실상 변경할 수 없습니다.** 기존 bank 메타데이터에 0이 아닌 `decimals`가 이미
기록되어 있으면 이를 변경하려는 모든 시도는 `cannot update denom metadata decimals` 오류로 실패합니다.
`decimals: 0` 상태인 denom만 값을 설정할 수 있습니다. 첫 번째 메타데이터 기록 전에 의도한 정밀도를 확인하세요.
`peggy0x...` 및 `ibc/...` denom에 대한 거버넌스 제안에서도 마찬가지입니다.
</Warning>

```protobuf
message MsgSetDenomMetadata {
  option (amino.name) = "injective/tokenfactory/set-denom-metadata";
  option (cosmos.msg.v1.signer) = "sender";

  string sender = 1 [ (gogoproto.moretags) = "yaml:\"sender\"" ];
  cosmos.bank.v1beta1.Metadata metadata = 2 [
    (gogoproto.moretags) = "yaml:\"metadata\"",
    (gogoproto.nullable) = false
  ];

  message AdminBurnDisabled {
    // admin burn 기능을 비활성화해야 하면 true
    bool should_disable = 1 [ (gogoproto.moretags) = "yaml:\"should_disable\"" ];
  }
  AdminBurnDisabled admin_burn_disabled = 3 [ (gogoproto.moretags) = "yaml:\"admin_burn_disabled\"" ];
}
```

**상태 변경:**

- 메시지 발신자가 denom의 admin인지 확인
- denom의 admin을 변경하고 admin burn 기능을 잠재적으로 비활성화하기 위해 `AuthorityMetadata` 상태 항목 수정


## 체인에서의 기대사항

체인의 주소에 대한 bech32 접두사는 최대 16자까지 가능합니다.

이는 SDK에서 적용되는 denom의 최대 길이가 128바이트이고, longest_subdenom이 44바이트로 설정된 것에서 비롯됩니다.

Token factory 토큰의 denom은 다음과 같습니다: `factory/{creator address}/{subdenom}`

구성 요소로 분리하면 다음과 같습니다:

- `len(factory) = 7`
- `2 * len("/") = 2`
- `len(longest_subdenom)`
- `len(creator_address) = len(bech32(longest_addr_length, chain_addr_prefix))`.

현재 가장 긴 주소 길이는 `32바이트`입니다. SDK 오류 수정 설정으로 인해 `len(bech32(32, chain_addr_prefix)) = len(chain_addr_prefix) + 1 + 58`이 됩니다.
이를 모두 더하면 총 길이 제약은 `128 = 7 + 2 + len(longest_subdenom) + len(longest_chain_addr_prefix) + 1 + 58`입니다.
따라서 `len(longest_subdenom) + len(longest_chain_addr_prefix) = 128 - (7 + 2 + 1 + 58) = 60`입니다.

longest_subdenom과 longest_chain_addr_prefix 사이에서 이 60바이트를 어떻게 분할할지에 대한 표준화 선택은 다소 임의적입니다.
이에 대한 고려 사항:

- [BIP-0173](https://github.com/bitcoin/bips/blob/master/bip-0173.mediawiki#bech32)에 따르면
  32바이트 주소('data field')에 대한 기술적으로 가장 긴 HRP는 31바이트입니다.
  (encode(data) = 59바이트, 최대 길이 = 90바이트에서 비롯됨)
- subdenom은 해시를 포함할 수 있도록 최소 32바이트여야 합니다
- 더 긴 subdenom은 사람이 읽을 수 있는 denom을 생성하는 데 매우 유용합니다
- 체인 주소는 더 짧은 것이 좋습니다. 현재까지 cosmos에서 가장 긴 HRP는 11바이트입니다. (`persistence`)

명확성을 위해 현재 `len(longest_subdenom) = 44` 및 `len(longest_chain_addr_prefix) = 16`으로 설정되어 있습니다.

SDK가 denom의 최대 길이를 128바이트에서 늘리면 이러한 제한도 증가해야 합니다.

따라서 파싱을 위해 이러한 최대 길이에 의존하는 코드를 작성하지 마십시오.
