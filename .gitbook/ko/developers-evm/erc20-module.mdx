### ERC20 모듈

ERC20 모듈은 **기존** bank denom(IBC 브릿지 토큰, USDC, TokenFactory 및 Peggy denom)을 Injective EVM에서 사용할 수 있게 합니다. 스토리지에 토큰 쌍 간의 매핑을 유지하여 ERC20 컨트랙트 주소를 해당 bank denom과 연결합니다. [Bank precompile](/ko/developers-evm/bank-precompile)은 이 매핑을 읽어 ERC20 호출이 어떤 denom에 대해 작동하는지 결정합니다. 이 모듈은 두 가지 목적을 수행합니다:

1. **스토리지**: bank denom ↔ ERC20 주소 간 매핑
2. **메시지 유형**: 사용자가 체인 메시지를 발행하여 새 토큰 쌍 매핑을 설정할 수 있음

<Note>
Bank precompile을 사용하여 Injective EVM에 직접 배포된 토큰은 토큰 쌍이 **필요하지 않습니다**. 해당 denom은 컨트랙트 주소로부터 `erc20:0x...` 형식으로 파생됩니다. 이 페이지는 네이티브 측에 이미 존재하는 denom의 페어링 경로를 다룹니다. 두 경로에 대한 개념적 개요는 [MultiVM Token Standard](/ko/developers-evm/multivm-token-standard)를 참조하세요.
</Note>

## 토큰 쌍 생성

세 가지 유형의 bank denom이 관련 토큰 쌍을 가질 수 있으며, 각각 다른 규칙이 적용됩니다:

| Denom | 페어 생성 가능 주체 | 사용자 정의 ERC20 주소 | 주소 생략 시 배포되는 템플릿 |
|---|---|---|---|
| **TokenFactory** `factory/...` | denom 관리자 또는 거버넌스 | 조건부 허용 | `MintBurnBankERC20`, 메시지 발신자가 소유 |
| **Peggy** `peggy0x...` | 누구나 | 거부됨 | `FixedSupplyBankERC20`, 소유자 없음 |
| **IBC** `ibc/...` | 누구나 | 거부됨 | `FixedSupplyBankERC20`, 소유자 없음 |

Peggy 및 IBC 페어링은 무허가(permissionless)이므로 템플릿이 강제됩니다. 이 조합은 의도된 것입니다. 누구나 브릿지된 토큰을 EVM에서 사용할 수 있게 만들 수 있지만, 아무도 자신이 제어하지 않는 denom에 자신의 컨트랙트를 연결할 수는 없습니다.

페어 생성자는 배포된 `MintBurnBankERC20`의 소유자가 됩니다. 거버넌스로 생성된 페어의 경우 해당 소유자는 거버넌스 모듈 주소입니다.

### 사전 요건: denom에 공급량이 있어야 함

페어 생성을 위해서는 bank denom이 이미 존재하고 공급량이 0이 아니어야 합니다. 첫 민트 전에 제출하면 `ErrUnknownBankDenom`으로 실패합니다. TokenFactory 출시의 경우 `MsgCreateDenom`, `MsgMint`, `MsgCreateTokenPair`를 하나의 원자적 트랜잭션으로 제출하여 세 단계가 어긋나지 않도록 하세요.

### Permissions 네임스페이스는 고정 공급량 템플릿을 강제함

TokenFactory denom에 `MINT`, `BURN` 또는 `SUPER_BURN`을 비활성화하는 **policy**가 있는 [permissions 네임스페이스](/ko/developers-native/injective/permissions)가 있는 경우:

- 체인은 `MintBurnBankERC20` 대신 `FixedSupplyBankERC20`을 배포하며,
- 메시지에 포함된 사용자 정의 ERC20 주소는 `ErrInvalidERC20Address`로 거부됩니다.

이 조건은 세 가지 작업에 대한 OR입니다. `BURN`만 비활성화해도 `FixedSupplyBankERC20`이 생성되며, 이 컨트랙트에는 민트 진입점이 전혀 없습니다.

<Note>
이는 역할(role) 권한이 아니라 작업에 대한 네임스페이스 **policy 상태**에 의해 결정됩니다. 명시적인 policy 상태 없이 생성된 네임스페이스는 모든 작업에 대해 허용적인 기본값으로 채워지므로, 역할만 정의해서는 고정 공급량 템플릿이 강제되지 않습니다. 명시적으로 비활성화된 policy만 이를 강제합니다.
</Note>

## 페어 생성 시 검증 항목

ERC20 주소가 제공되면 모듈은 다음을 확인합니다:

1. bank denom 또는 ERC20 주소에 대한 토큰 쌍이 이미 존재하지 않을 것,
2. 해당 주소의 계정이 존재하고 컨트랙트 코드를 보유할 것,
3. 파생된 `erc20:0x...` denom에 **유통 공급량과 bank 메타데이터가 모두 없을 것**. 그렇지 않으면 `ErrExistingERC20DenomSupply`,
4. 컨트랙트가 300,000 가스 한도 내에서 `symbol()` 호출에 응답할 것. 그렇지 않으면 `ErrInvalidERC20Address`.

<Warning>
**검증을 통과했다고 해서 컨트랙트가 MTS 호환이라는 의미는 아닙니다.** `symbol()` 검사는 해당 주소에 ERC20 형태의 무언가가 있다는 것만 확인합니다. 일반 OpenZeppelin ERC20은 위의 모든 검사를 통과하면서도 잔액을 bank 모듈과 완전히 분리된 자체 EVM 스토리지에 보관합니다. 그 결과 양쪽이 서로 일치하지 않는 페어가 생성됩니다.

이를 복구하려면 거버넌스 `MsgDeleteTokenPair`로 매핑을 제거한 후 호환되는 컨트랙트로 새로 등록해야 합니다. 매핑을 삭제해도 이미 어긋난 잔액은 조정되지 않습니다. 페어링 후가 아니라 페어링 전에 구현을 검증하세요.
</Warning>

이름과 달리 `ErrExistingERC20DenomSupply`는 **공급량 또는 메타데이터**가 있을 때 발생합니다. 생성자에서 메타데이터를 기록한 컨트랙트는 공급량이 0이어도 거부됩니다.

## TokenFactory Denom용 사용자 정의 컨트랙트

사용자 정의 컨트랙트는 잔액, 공급량, 전송, 민트 및 버닝을 Bank precompile을 통해 라우팅해야 합니다. 이를 보장하는 실용적인 방법은 정확히 그 위임을 구현한 [Injective의 Solidity 컨트랙트](https://github.com/InjectiveLabs/solidity-contracts)의 `BankERC20`을 확장하는 것입니다.

### 빈 메타데이터로 배포

`BankERC20`의 생성자는 name 또는 symbol이 비어 있지 않거나 decimals가 0이 아닐 때마다 `bank.setMetadata`를 호출합니다. 페어링되지 않은 컨트랙트의 경우 precompile은 denom을 `erc20:0x<contract>`로 결정하므로, 이 호출은 원하지 않는 denom에 메타데이터를 기록하게 되고 이후 페어 생성은 `ErrExistingERC20DenomSupply`로 실패합니다.

빈 name, 빈 symbol, 0 decimals로 배포하세요. 이는 스타일상의 선호가 아니라 페어링 경로에서 강제되는 요구 사항입니다.

```solidity
// SPDX-License-Identifier: Unlicense
pragma solidity ^0.8.20;

import {BankERC20} from "./BankERC20.sol";

/// Pairs with an existing TokenFactory denom.
/// Empty constructor metadata keeps the BankERC20 constructor from calling
/// bank.setMetadata, which would create an erc20:0x... denom and block pairing.
contract FactoryPairedERC20 is BankERC20 {
    constructor() BankERC20("", "", 0) {}
}
```

`BankERC20`은 `abstract`이므로 단독으로 배포할 수 없습니다. 페어링 후 `name()`, `symbol()`, `decimals()`는 precompile을 통해 **factory denom**의 bank 메타데이터로 결정되며, 이는 denom 관리자가 `MsgSetDenomMetadata`로 제어합니다.

같은 이유로 페어링 전에 독립적인 `erc20:0x...` 공급량을 민트하지 마세요.

<Note>
이는 EVM 직접 배포와 정반대입니다. 직접 배포에서는 컨트랙트 자체의 파생 denom이 **곧** 토큰이므로, 생성자에서 메타데이터를 설정하고 `erc20:0x...` 공급량을 민트하는 것이 의도된 경로입니다. [MultiVM Token Standard](/ko/developers-evm/multivm-token-standard)를 참조하세요.
</Note>

## 민트 및 버닝 권한

ERC20 소유권과 네이티브 TokenFactory 권한은 별개의 검사이며, 하나를 충족한다고 다른 하나가 충족되지 않습니다. 이는 이 경로에서 가장 흔히 겪는 예상치 못한 문제입니다.

`MintBurnBankERC20.mint()`는 `onlyOwner`이므로 EVM 호출자는 컨트랙트 소유자여야 합니다. 그런 다음 호출은 Bank precompile에 도달하며, precompile은 EVM 호출자가 아닌 **ERC20 컨트랙트 주소를 발신자로 하여** 네이티브 `MsgMint`를 제출합니다. 따라서 네이티브 검사는 컨트랙트 주소에 적용됩니다:

| Denom 구성 | ERC20 컨트랙트 주소의 요건 |
|---|---|
| permissions 네임스페이스 없음 | TokenFactory denom 관리자여야 함 |
| permissions 네임스페이스 있음 | `MINT` 권한을 보유해야 함. 관리자인 것만으로는 충분하지 않음 |

버닝은 더 엄격합니다. ERC20 `burn()` 또는 `burnFrom()`은 컨트랙트를 발신자로, 보유자를 burn-from 주소로 하는 `MsgBurn`으로 체인에 도달하므로, 셀프 버닝이 아닌 burn-from이 됩니다:

| Denom 구성 | ERC20 버닝 요건 |
|---|---|
| permissions 네임스페이스 없음 | denom에 `allow_admin_burn`이 설정되어 있고, **그리고** 컨트랙트 주소가 denom 관리자일 것 |
| permissions 네임스페이스 있음 | denom에 `allow_admin_burn`이 설정되어 있고, **그리고** 컨트랙트 주소가 `SUPER_BURN`을 보유할 것 |

<Warning>
`allow_admin_burn`은 `injectived tx tokenfactory create-denom`에서 기본값이 **false**이며 생성 시에만 설정할 수 있습니다. 이는 단방향 래치입니다. 한 번 false이거나 비활성화되면 다시 활성화할 수 없습니다. `--allow-admin-burn` 없이 생성된 denom은 페어링된 ERC20을 통해 절대 버닝할 수 없습니다. denom을 생성하기 전에 이를 결정하세요.
</Warning>

`MsgChangeAdmin`으로 denom 관리자를 변경해도 ERC20의 `owner()`는 변경되지 않으며, ERC20 소유권을 이전해도 denom 관리자는 변경되지 않습니다. 하나를 교체하면 다른 하나도 교체하세요.

### 컨트랙트 권한 부여

페어링된 ERC20을 통해 민트하려면 컨트랙트 주소가 네이티브 측에서 권한을 부여받아야 합니다. 두 주소는 서로 다른 인코딩의 동일한 계정이므로, 먼저 EVM 주소를 bech32 형식으로 변환하세요:

```bash
npm install @injectivelabs/sdk-ts

TOKEN="0xYOUR_PAIRED_ERC20"

TOKEN_INJ=$(
  node --input-type=module - "$TOKEN" <<'JS'
import { getInjectiveAddress } from '@injectivelabs/sdk-ts'
console.log(getInjectiveAddress(process.argv[2]))
JS
)
```

그런 다음 `MsgChangeAdmin`으로 denom 관리자를 `TOKEN_INJ`로 이전하거나, permissions 네임스페이스에서 `MINT`를 포함하는 역할을 부여하세요. 관리자를 이전하면 컨트랙트가 단독 민트 권한을 갖게 되므로 ERC20 소유자 키를 안전하게 보관하세요. 그 키가 민트할 수 있는 유일한 방법이 됩니다.

## 출처별 메타데이터 권한

| 출처 | Denom | bank 메타데이터 설정 가능 주체 |
|---|---|---|
| TokenFactory | `factory/...` | denom 관리자, `MsgSetDenomMetadata`를 통해, 즉시 적용 |
| Peggy | `peggy0x...` | 거버넌스 제안만 가능 |
| IBC | `ibc/...` | 거버넌스 제안만 가능 |
| Injective EVM | `erc20:0x...` | 컨트랙트 자체, precompile의 `setMetadata`를 통해 |

Peggy 및 IBC denom은 name, symbol, decimals 없이 도착하며, Injective의 어떤 계정도 이를 직접 설정할 권한이 없습니다. 지갑에 이미 빈 토큰이 표시된 후 정리 작업으로 처리하기보다는 출시 계획의 일부로 거버넌스 제안을 준비하세요.

<Warning>
Decimals는 사실상 한 번만 기록할 수 있습니다. bank 메타데이터에 0이 아닌 `decimals`가 기록되면 변경 시 `cannot update denom metadata decimals`로 실패합니다. 첫 번째 기록에서 올바른 값을 설정하세요.
</Warning>

## 실습 예제: 사용자 정의 컨트랙트 페어링

이 예제는 테스트넷에서 사용자 정의 컨트랙트를 기존 TokenFactory denom과 페어링합니다.

```bash
# Endpoints and identifiers
ENDPOINT="https://testnet.sentry.lcd.injective.network"      # LCD / REST
NODE="https://testnet.sentry.tm.injective.network:443"       # native RPC
EVM_RPC="https://testnet.sentry.chain.json-rpc.injective.network"
CHAIN_ID="injective-888"

# ADMIN_KEY is an injectived keyring name; ADMIN is the bech32 address it holds
ADMIN_KEY="admin"
ADMIN=$(injectived keys show "$ADMIN_KEY" -a)
DENOM="factory/${ADMIN}/acme"
```

빈 메타데이터로 컨트랙트를 배포한 후 페어링합니다:

```bash
forge create src/FactoryPairedERC20.sol:FactoryPairedERC20 \
  --account acme-deployer \
  --rpc-url "$EVM_RPC" \
  --broadcast

TOKEN="0xDEPLOYED_ADDRESS"

injectived tx erc20 create-token-pair "$DENOM" \
  --erc20 "$TOKEN" \
  --from "$ADMIN_KEY" \
  --chain-id "$CHAIN_ID" \
  --node "$NODE" \
  --gas 3000000 \
  --gas-prices 160000000inj
```

체인이 대신 `MintBurnBankERC20`을 배포하도록 하려면 `--erc20`을 생략하세요.

두 뷰가 일치하는지 확인합니다:

```bash
# Resolve the pair directly rather than listing every pair
curl --fail --silent --show-error --get \
  "$ENDPOINT/injective/erc20/v1beta1/token_pair_by_denom" \
  --data-urlencode "bank_denom=$DENOM" | jq

# ERC20 view, which should reflect the factory denom's metadata
cast call "$TOKEN" "name()(string)"     --rpc-url "$EVM_RPC"
cast call "$TOKEN" "symbol()(string)"   --rpc-url "$EVM_RPC"
cast call "$TOKEN" "decimals()(uint8)"  --rpc-url "$EVM_RPC"

# Bank view
curl --fail --silent --show-error --get \
  "$ENDPOINT/cosmos/bank/v1beta1/denoms_metadata_by_query_string" \
  --data-urlencode "denom=$DENOM" | jq '.metadata'
```

컨트랙트 주소가 네이티브 측에서 권한을 부여받기 전에 EVM에서 민트하면
`failed to mint: unauthorized account`로 revert됩니다. `BankERC20`은 precompile의 revert를 포착하여 접두사를 붙이므로,
근본 원인은 ERC20 `onlyOwner` modifier가 아니라 TokenFactory 권한 검사입니다.
위에서 설명한 대로 컨트랙트에 권한을 부여한 후 다시 시도하세요.

## 가스

`MsgCreateTokenPair`는 템플릿 배포에 2,000,000 EVM 가스 한도를 부여합니다. 이는 컨트랙트 배포 예산이며 트랜잭션 전체 가스가 아닙니다. 트랜잭션 전체에는 ante 처리와 트랜잭션 내 다른 메시지도 포함됩니다. 단독 페어 생성에는 최소 `--gas 3000000`을 사용하세요. 약 2.1M 미만에서는 트랜잭션이 가스 계산 오류로 실패합니다. 릴리스마다 고정된 숫자에 의존하기보다는 `POST /cosmos/tx/v1beta1/simulate`로 시뮬레이션하고 여유분을 적용하세요.

## 토큰 쌍 삭제

`MsgDeleteTokenPair`는 거버넌스로 제한됩니다. 이는 매핑만 제거합니다. 어느 쪽의 잔액도 마이그레이션, 조정 또는 버닝하지 않습니다.
