# Bank Precompile

Bank Precompile 是一个位于固定地址 `0x0000000000000000000000000000000000000064` 的系统智能合约。

它为 EVM 开发者提供了一种高效且原生的方式来直接与 Injective 的 **bank 模块**（`x/bank`）交互。这有效地将 ERC-20 token 带到链上。任何使用 Bank precompile 的 ERC-20 合约将在链上表示为 `erc20:0x...` denom。从技术上讲，这意味着 token 仅存在于链上，EVM 提供链状态的视图而不是维护单独的副本。与传统桥接不同，传统桥接需要用户操作来切换两个 token 版本，Bank precompile 为使用链上 bank denom 或 ERC-20 `transfer()` 方法的任何转账提供实时、双环境反映。

一系列由 Bank precompile 支持的 ERC-20 实现，以及 precompile 接口和抽象合约，可在 [Injective 的 Solidity 合约仓库](https://github.com/InjectiveLabs/solidity-contracts) 中找到。关键合约包括：

* **Bank.sol** – precompile 接口
* **BankERC20.sol** – 由 Bank precompile 支持的抽象 ERC20 实现
* **FixedSupplyBankERC20.sol** – 固定供应量的去中心化 ERC20（无所有者，无铸造或销毁）
* **MintBurnBankERC20.sol** – 具有授权铸造和销毁 token 的所有者的 ERC20

这些实现基于 OpenZeppelin 的 ERC20 合约。开发者可以自由创建使用 Bank precompile 的自定义 ERC20 合约。

## Denom 创建费用

为防止 denom 垃圾信息，创建一个新的 `erc20:0x...` denom 需要 **1 INJ**，可在
`/injective/erc20/v1beta1/params` 查询。

该费用在**首次铸造**时收取，而不是在部署时，并且从**合约自身的
INJ 余额**中扣除，而不是从调用者扣除。`BankERC20` 的构造函数是 `payable` 的，因此
部署交易可以预先为合约注入资金，这也是它常被称为
部署费用的原因。

<Warning>
只要 denom 的供应量为零就会触发收费，而不仅仅是在其生命周期中收取一次。如果总
供应量回到零，该 denom 将从状态中移除，下一次铸造会重新创建它并再次收取
费用。如果在全部销毁后可能恢复铸造，请保持合约有足够资金。
</Warning>

## Bank Precompile 接口

```solidity
interface IBankModule {
    function mint(address,uint256) external payable returns (bool);
    function balanceOf(address,address) external view returns (uint256);
    function burn(address,uint256) external payable returns (bool);
    function transfer(address,address,uint256) external payable returns (bool);
    function totalSupply(address) external view returns (uint256);
    function metadata(address) external view returns (string memory,string memory,uint8);
    function setMetadata(string memory,string memory,uint8) external payable returns (bool);
}
```

### Denom 解析

每个方法在操作状态之前，都会将调用合约的地址解析为一个 bank denom：

1. 如果 ERC20 模块为该地址注册了 **token 对**，则使用配对的 bank denom
   （`factory/...`、`peggy0x...` 或 `ibc/...`），
2. 否则，denom 派生为 `erc20:0x<ChecksummedAddress>`。

这就是为什么与 TokenFactory denom 配对的合约会报告该 denom 的元数据和供应量，而
未配对的合约拥有自己的 `erc20:` denom。两种情况下合约代码完全相同，只有
注册条目不同。

### 方法语义

| 方法 | 值得了解的行为 |
|---|---|
| `mint` / `burn` | 对于 `erc20:` denom，ERC20 模块直接铸造或销毁。对于已配对的 TokenFactory denom，precompile 会提交一个原生 `MsgMint` 或 `MsgBurn`，**以合约地址作为发送者**，因此原生授权作用于合约，而不是 EVM 调用者。已配对的 Peggy 和 IBC denom 两者都不支持。 |
| `setMetadata` | 仅对 `erc20:` denom 有效。在与 TokenFactory、Peggy 或 IBC denom 配对的合约上调用时，会以 `denom ... does not support setting metadata through bank precompile` 回滚。这些 denom 的元数据需在原生侧设置。 |
| `metadata` | 读取所解析 denom 的 bank 元数据。 |
| `balanceOf` / `totalSupply` / `transfer` | 读取和写入所解析 denom 的 bank 状态。 |

<Warning>
只要 name 或 symbol 不为空，或 decimals 不为零，`BankERC20` 的构造函数就会调用 `setMetadata`。
对于打算与现有 TokenFactory denom 配对的合约，这会为
错误的 denom 写入元数据并阻止配对。请以空 name、空 symbol 和零 decimals 部署这类合约。请参阅
[ERC20 Module](/cn/developers-evm/erc20-module#tokenfactory-denom-的自定义合约)。
</Warning>
